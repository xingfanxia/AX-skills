# Repository context

Use repository evidence to understand the current task, not to assign a
permanent process tier.

Read applicable instructions, manifests, relevant entry points, tests, and
source-of-truth documentation. Identify generated outputs, ownership boundaries,
and available verification commands. A schema directory, UI dependency, or
large content collection is a discovery signal, not a workflow command.

Judge risk from the change itself. A documentation edit in a payment repository
can be direct; a new payment boundary in a blog deserves careful contract
analysis. Existing project preferences guide routine choices, while current
evidence can reveal that a preference does not fit this task.

When the initial understanding is wrong, correct it as soon as evidence shows
why. Do not wait for repeated failed phases or write a durable profile merely
because the skill ran.
